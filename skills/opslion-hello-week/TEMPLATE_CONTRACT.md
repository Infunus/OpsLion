# OpsLion Hello Week Skill v4.0.1：原生模板与内容契约

## 1. 输入和输出

本 Skill 的单一真实样式来源是随包的 `hello-week.template.json`（`hello-week/native-v2`）；它由用户上传的秀米 v5 原生推文抓取包提取而来。每期正文由当期素材提取，不复用旧活动事实。旧版 Hello Week 文案 Skill 的时间处理、事件去重和证据规则已整合于 `SKILL.md`、`references/source-workflow.md`、`references/writing-style.md`；本文件约定原生模型与关键文案门槛。

每期按 `starter.json` 编写 UTF-8 JSON 数据，运行 `scripts/build.py`，交付 **`xiumi-bridge/v4` 的 `.xiumi.json`**，交给 支持 xiumi-bridge/v4 原生协议的 OpsLion 插件。禁止输出 v3 HTML 混用包、截图代替原生排版或手写一个仿制的前端页面。

## 2. 内容结构

- 标题：`Hello Week丨...`，按实际学期与周次填写，不沿用示例期次。
- `submission.enabled`：投稿说明；默认保留原文投稿区、二维码及头像装饰。二维码是否有效应核对。
- `review`：上周回顾。元素为 `{ "name": "学术信息", "items": [...] }`，每个 `items` 内为资讯。
- `upcoming`：下周及后续；格式同 `review`。
- `shows_panel`（百讲演出）：**每期无条件保留**，固定放在后续资讯之后、重要提示之前。AI 不负责填充，保留“下周百讲演出速览”标题与浅蓝色原生方框，内部**只有一个完全空白的秀米原生文本组件**。不再使用 `performances` 输入字段。
- `notices`：可选重要提示，元素 `{ "title": "...", "body": "..." }` 或 `fields`；无内容则整个提示分区及过渡词一并省略。
- `contact.enabled`、`contact.email`：固定联系区；负责人联系方式仅在获得当期确认时提供 `contact.other`。
- `credits.copy`、`credits.layout`、`credits.proofread`：文案、排版、校对，保持原生右对齐，默认为空待填写。

资讯条目示例：

```json
{
  "title": "本期资讯标题",
  "fields": [
    {"label": "时间", "value": "有依据的日期、星期、时间段"},
    {"label": "地点", "value": "有依据的地点"},
    {"label": "报告人", "value": "有依据时才填写"},
    {"label": "内容", "value": "简明概括，不删必要条件"}
  ],
  "link": {"label": "原文标题", "url": "https://example.com/article"}
}
```

字段按来源存在与否决定；不需要的字段直接从列表删除。需要两场以上日程时可以用多个字段保留完整时间和场次。没有对应资讯栏目或条目时删除数据项，**不要生成虚构活动或历史信息**。唯一保留的空白内容区域是必备的百讲演出方框，交由用户自行填写。

## 3. 资料选择与文案生成（必须先筛选，后排版）

### 3.1 两个时间分区，采用不同的入选标准

**上周回顾 `review`：只收与信息科学技术学院本科生直接相关的已发生事项。**

- 优先：信科本院主办、承办、面向信科本科生举办，或信科本科生实际参与并构成活动主要内容的学术、活动、比赛与通知
- **校学生会、计算机学院、集成电路学院等渠道发布的内容，不因与北大同属一校、或研究方向相近，就自动纳入回顾**。只有来源明确表明其与信科本科生有关（面向信科本科生、信科本科生参加/获奖、信科本院联合举办等），才收录
- 对“是否与信科本科生有关”证据不足的活动，默认**不写入回顾**。不能仅凭来源公众号名称或“院系同属计算机领域”推断

**下周及后续 `upcoming`：收所有与信科本科生相关、或信科本科生实际可以参加的未来事项。**

- 可包括信科本院及其他院系、校学生会、学校或校外组织的信息，只要确有**可参与性或明确的相关性**，并且活动/报名/截止时间尚未结束
- “可以参加”须结合来源给出的对象、年级、身份、专业、人数限制、报名要求及活动时间确认；面向研究生专属或其他限定群体且本科生不符合条件的，不能因为活动很有价值就纳入
- 纯宣传、面向其他群体、没有本院本科生关联的历史活动，即使来自常用信息源，也不应收录

**时间归档以活动发生时间和有效报名/截止节点为准**，不能单凭推文发布日期判定。对跨期活动，回顾写上周实际发生的内容，预览写仍有参与意义的后续安排；避免同一事实在两区重复。

### 3.2 已结束活动：重视读者真正需要的信息

- 回顾应回答：**发生了什么、与信科本科生有什么关系、有何值得关注的结果或内容**
- 不要写“报名人数、报名人次、报名总数、多少人报名、报名踊跃”等无后续参考价值的招募统计；也不保留已失效的报名方式、截止倒计时与动员口吻
- 允许保留**具有新闻价值的实际结果**，如比赛名次、获奖情况、已举办讲座的核心内容；“多少人参与”只有在规模本身是事件关键信息且对读者有明确意义时才酌情保留
- 回顾尽量用完成态表达，避免已结束活动继续写“欢迎报名、即将举行”

### 3.3 行文与标点

- **每条资讯的文案末尾、自然段结尾、信息字段末尾不加中文句号 `。`**。段内有多个完整句子时，可正常使用句号；只去掉段落最后的句号
- 保留必要的问号、叹号、引号，以及原文正式标题、专名、缩写、URL 中的标点，不为了去句号误改事实或引用
- 表述精炼、客观，保留日期、星期、时间段、地点、报告人、活动要点、必要的参加对象及报名/截止条件（仅限仍有效的未来活动）。缺失字段直接省略
- 从用户给出的素材和来源提取事实，核实举办日期、受众和资格、去重；不得自行编造人数、日程、活动结果和参与条件
- 默认 `links_enabled:true`，省略时同样开启；“详情请见：原文标题”默认链接到采集到的真实原文地址，不加下划线。地址缺失时仅显示标题并提示缺失，不猜测或拼接地址。用户明确要求关闭时设为 `false`
- 尊重原稿主要叙事和重点；可以合理压缩重复宣传句、拆分长段，不为了适配组件而大规模删改文案

### 3.4 出稿前逐条检查

1. **回顾相关性**：能否在材料中指出“信科本科生关联”的具体证据？不能就删除
2. **预览参与性**：能否确认信科本科生可参与，或活动与其明确相关？是否仍在有效期内？
3. **已结束活动**：是否仍写了报名人数、已失效的报名条件/宣传语，或无意义的过程性数据？
4. **结尾标点**：每条生成的说明和字段末尾是否还有句号？仅处理结尾，不破坏段内句号及原文标题
5. **信息核对**：时间、地点、主讲人、参加条件及“详情请见”均有来源支持；无来源的不补写

**这些是撰稿与筛选规则，不能只靠关键词匹配代替语义判断。** 生成脚本只做简单的段尾句号处理和显式无效统计字段提示；选题相关性由撰稿阶段结合来源判断。

### 3.5 采编、去重与更正（旧版 Skill 的关键规则已适配）

- 逐篇阅读实际来源材料，从合集拆分独立事件；同一事件多篇预告/报道/更新只生成一条，不能把不同场次或届次误合并
- 以活动举办、报名/材料提交、执行等实际时间节点归档，不能仅凭公众号发布时间决定是否入选；先处理改期和取消，再判断有效时间范围
- 每条公开事实都能回到本期资料或明确人工定稿核实；来源公众号、发文日期、证据定位属于内部采编信息，不写进正文
- 先整理真实事件和目标读者，再按原生组件的语义作用选择和重排；不以旧版抓取顺序反推或大规模改写内容
- 如输入为批量公众号文章，按 `references/source-workflow.md` 建立内部候选事件记录；详细写作和校稿见 `references/writing-style.md`、`references/editorial-review.md`

## 4. 排版设计约束

1. **保持源稿的组件与固定栏目顺序**：开场、投稿、回顾（可省略）、预览（可省略）、必备百讲空白框、重要提示（可省略）、联系区及结尾落款；动图、蓝色渐变标签、蓝底白字标题条、浅蓝背景正文、章节图标均来自原生组件树。
2. 按内容改变新闻数量时，复制并重编模块内部的原生组合子组件；不重新发明 HTML 卡片，不加圆角阴影等额外 AI 风格装饰。
3. 内容增长导致窄容器溢出时，优先修复相应容器的伸缩约束和换行能力。标题条原有背景、字体、配色、边距、装饰原则上保持。
4. 本脚本已经对资讯标题的原生容器设置 `flex:0 1 auto`、`minWidth:0`、`maxWidth:100%`，避免过长文字撑开父级。**实际截断与换行需在秀米编辑器验证**。
5. 长文、二维码、特殊混排仍需看实际结果；仅由数据结构和脚本不能保证视觉无误。百讲方框内不放海报，由用户导入后自行完善。
6. **首行缩进与西文打断默认都关闭**。Hello Week 常规浅蓝资讯框（包括长正文）保持原生无缩进样式；不能用字数阈值决定首行缩进。确有特殊排版需求时，单条资讯可明确设置 `typography.first_line_indent: "2em"`；仅当连续长西文确实影响折行时显式设置 `typography.western_break: true`。`first_line_indent` 省略或设为 `"none"` 时不缩进；旧数据中的 `"auto"` 为兼容保留，但现在也按不缩进处理。`western_break: "auto"` 仅在**显式指定**后才执行长西文启发式判断。详见 `references/typography-and-layout.md`。

## 5. 成稿审核顺序

- **事实**：去重、核对时间/地点/人物/链接/活动性质、检查是否误用参考文章的往期内容；分别按 §3.1 的回顾与预览标准筛选。
- **文案**：去除回顾中无价值的报名统计及失效招募口吻，逐段检查正文末尾无句号，保留段内标点与正式标题。
- **结构**：普通资讯栏目有内容才出现、分类和新闻成对、标题正确定义、信息排布顺序合理、落款不漏。**百讲演出为例外，每期必须保留，框内恰好一个空白原生文本框。**
- **模型**：必须是 v4 原生结构，来源模板的组件样式 intact、编辑位置可解析、图片地址可上传，不能发生重复 UUID。
- **视觉风险**：长标题折行，固定尺寸文字框、父容器 `flex`、多栏目间留白、海报比例、装饰遮挡、内容文字是否溢出。对具体风险做局部修复而不是统一缩小字号。
- **实际视觉**：如有秀米可访问的编辑环境，导入后用手机预览观察实际排版；没有时说明尚未完成真实渲染验证。
- **交付**：输出最终 `.xiumi.json` 和必要的待核对事项即可，避免把审核报告和多个不必要的副本混入成稿。

## 6. 一次导入模板

直接导入包 `HelloWeek_原生模板示范稿.xiumi.json` 是**有占位信息的可编辑演示稿**。正式生成时必须重新用 `weekly-content.json` 构建，不应直接发布演示稿。

> 逐组件能力、输入字段、自动顺序与使用限制详见 `component-guide.md`；不同类型的组合样例详见 `examples/`。
