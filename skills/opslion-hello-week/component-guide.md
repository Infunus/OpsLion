# Hello Week Skill v4.0：14 种原生组件的使用手册

**本手册描述 `hello-week.template.json → seeds` 中真实存在的 14 类组件。** 这些组件来自《Hello Week丨26春 第十周》的原生秀米抓取模型，保留原来的层级、图片、样式。生成器按照 `weekly-content.json` 组装，不需再造 HTML 版式。

## 总览

| 原生种子 ID | 显示形式和用途 | 如何控制 | 使用频率 |
| --- | --- | --- | --- |
| `banner` | 顶部 Hello Week 动图 | 自动 | 每期一次 |
| `code_intro` | `#include`、EECS、`printf` 代码开场 | 自动，暂不开放逐行改写 | 每期一次 |
| `divider` | `＞＞＞-----` 文字分隔 | 在分区前后由生成器自动插入 | 按需多次 |
| `submission` | 投稿说明、装饰头像和二维码、奖励提示框 | `submission.enabled` | 通常每期一次 |
| `section` | 章节图标 + “上周回顾”等大标题 | `review` / `upcoming` / `notices` 自动触发 | 每区一次 |
| `news_panel` | 分类渐变条 + 蓝底资讯标题和正文的组合 | `review[]`、`upcoming[]` | 每个非空大区一次 |
| `transition_review` | 回顾到后续的代码式过渡 | 两个大区都有内容时自动插入 | 按需 |
| `shows_panel` | 百讲演出标题及浅蓝色内容方框 | 自动，无需输入字段 | **每期必备** |
| `transition_notice` | 提醒前的代码式过渡 | `notices[]` 非空自动插入 | 按需 |
| `notice_panel` | 一个或多个提示标题和内容 | `notices[]` | 按需 |
| `contact` | 联系方式说明 | `contact.enabled` 和各联系字段 | 通常每期一次 |
| `code_outro` | `printf` / `return 0` 结尾代码 | 自动 | 每期一次 |
| `credits` | 右对齐的组织落款、文案/排版/校对 | `credits` 对象 | 每期一次 |
| `footer` | 文末学院落款图片 | 自动 | 每期一次 |

### 1. `banner` — 栏目动图

**来源：** `paper-cp:image/img-autowidth`。默认放在全文最开始，原生 GIF 图片，生成器直接保留。无需写 `banner` 字段；不要把它替换成静态截屏。若栏目视觉素材更新，应在组件库里更换图片来源，再重新出包。

### 2. `code_intro` — 代码风格开场

**来源：** 原生文本组件，包含 `#include <this week>`、`#include <next week>`、`using namespace EECS;` 和栏目介绍代码。生成器固定输出这一组件。保留源稿的代码高亮格式和换行；修改内容时针对文本片段而非整体重造 HTML。

### 3. `divider` — 箭头和短横线分隔

**来源：** 原生文本组件，显示 `＞＞＞--------------------------------`。生成器在投稿区和大分区之间、演出和提醒前按需插入。通常不需要人为调节数量；短周报应少分隔，不生成连续空分隔线。

### 4. `submission` — 投稿说明与二维码

**控制：**

```json
"submission": { "enabled": true }
```

`false` 时整块省略。该组件是一组真实嵌套布局，包含投稿文字、二维码、装饰头像和蓝色提示框。默认完整保留来源稿的固定介绍。**二维码和奖励文字涉及现实运营信息，应核对本期是否仍有效。** 如需改投稿文案、替换二维码，请基于当前源稿原生子组件定位后做修改，不能只在内容数据 JSON 中写一个未实现的 `submission.body` 字段。

### 5. `section` — 大分区

**自动触发条件：** `review` 非空时输出“上周回顾”，`upcoming` 非空时输出“下周及后续”，`notices` 非空时输出“重要提示”。保留原生章节图标、位置和字号。没有资讯时不应输出空标题。

### 6. `news_panel` — 分类与资讯（核心）

这是**一个顶层原生组合组件**，内部依次放多个「分类标题 → 资讯标题 → 资讯内容」。可以任意增减条目，但所有新增条目仍是秀米原生子组件。

**数据格式：**

```json
"review": [
  {"name": "学术信息", "items": [
    {"title": "示例学术报告", "fields": [
      {"label": "日期", "value": "2026年11月20日（星期五）"},
      {"label": "时间", "value": "14:00—16:00"},
      {"label": "地点", "value": "示例报告厅"},
      {"label": "主讲人", "value": "示例研究者"},
      {"label": "内容", "value": "依据来源填写简介"}
    ], "link": {"label": "该报告原文标题", "url": ""}}
  ]},
  {"name": "活动信息", "items": [
    {"title": "示例校园活动", "body": "没有结构化字段时，可以用自由段落简述"}
  ]}
]
```

上例的时间、地点、人名均为**虚构的结构演示**，不能当作本期事实。`upcoming` 格式完全相同。`fields` 是有序数组，可添加“报名截止、参与条件、场次、提交材料、报名方式”等字段，也可省略任何未知字段。`body` 可填字符串或字符串数组。无需固定某条资讯必须有时间地点。

**注意：`review` 与 `upcoming` 的选材门槛不同。** 回顾只记录有明确证据与信科本科生相关的已发生事项；校学生会、计算机学院、集成电路学院来源的普通历史活动不得直接当作信科回顾。预览则按“信科本科生可参加或确有相关性”筛选，不限制发布渠道。具体判断与例外见 `TEMPLATE_CONTRACT.md` §3.1，以及 `references/source-workflow.md`。

**文案处理：** 已结束活动只提有读者价值的事实和成果，不写报名人数等无用招募统计。正文和字段末尾不加句号；段内多个句子可保留句号。后续活动才按实际需要保留有效报名办法、截止与参加条件。

**三种内部子组件：**

- 类别标题：蓝色渐变、圆角和横线，`name` 决定文字。新的分类再写一项 `{"name":...,"items":...}`
- 资讯标题：蓝底白字标题条，`title` 决定文字；长标题通过收缩约束尽量允许换行，不裁剪掉内容
- 资讯正文：浅蓝信息区，`fields` 与 `body` 分段输出；字段前沿用原生蓝色勾选符。来源 `link.label` 生成“详情请见：”行，默认将标题链接到 `link.url` 中采集到的真实原文地址，不加下划线；缺失地址时保留普通文字并提示

**示例：两个类别、三条资讯** = `review` 写两个分类、分别放 1 条和 2 条 `items`。不会因此创建两套各自不一致的视觉设计。

### 7. `transition_review` — 回顾→后续过渡

两侧内容都有时自动生成一段 `printf` 风格的过渡代码。无需填写字段。如果只有 `review` 或只有 `upcoming`，自动省略，避免出现“看完上周信息”却根本没有上周内容的尴尬。

### 8. `shows_panel` — 百讲演出（固定保留、用户手工填写）

**每期必备，不能因当期资料缺失而删掉。** 保留源稿的“下周百讲演出速览”标题和浅蓝背景方框，固定放在“下周及后续”资讯之后、“重要提示”（如有）之前；没有下周资讯时也保留在正文后、联系区前的对应位置。

方框内部**只有一个真正空白的秀米原生文本组件**（`<p><br></p>`），不预填任何演出名称、日期、海报、链接、占位提示词或往期资料。用户在导入秀米后自行编辑。框内可从秀米继续添加图片等内容；AI 生成文件时不要擅自填充。

内容 JSON **不需要 `performances` 字段**。生成脚本无条件加入这一模块，即使 `review`、`upcoming`、`notices` 全部为空也不会删除。原生文本框不附带旧版“点击查看详情”的链接。

### 9. `transition_notice` — 提示过渡

当 `notices[]` 非空时自动出现，使用原稿的代码式过渡。没有提示时也不出现对应提示分区。

### 10. `notice_panel` — 重要提示

```json
"notices": [
  {"title": "示例提醒", "fields": [
     {"label": "时间", "value": "以当期通知为准"},
     {"label": "注意", "value": "应保留准确要求与截止条件"}
  ]},
  {"title": "另一条提醒", "body": "可自由写一段简短说明"}
]
```

`title` 必填；`fields` / `body` 格式与资讯一致。每个提示都复制原生标题和正文片段；没内容就删掉，不留空框。

### 11. `contact` — 联系渠道

```json
"contact": {
  "enabled": true,
  "email": "example@example.com",
  "message": "欢迎通过以下方式联系我们。",
  "other": "其他经过当期确认的联系方式"
}
```

`enabled:false` 可省略整块。`email` 是可修改的公共邮箱；`other` 可省略。不要在模板中永久硬编码临时负责人私人联系方式或未经确认的电话号码。该组件保留浅蓝背景和布局，但内容由本期数据替换。

### 12. `code_outro` — 代码式收尾

生成器自动在联系区或最后一个动态区后插入 `printf("我们下期再见!"); return 0;` 形式的原生代码文本。即使当期没有资讯，仍作为固定栏目结尾。

### 13. `credits` — 文案、排版、校对

```json
"credits": {
  "organization": "北京大学信息科学技术学院学生会",
  "copy": "",
  "layout": "",
  "proofread": ""
}
```

三项值为空时显示“文案丨 / 排版丨 / 校对丨”，后面留空待补；不用自造署名。保留原生右对齐。

### 14. `footer` — 底部落款图

生成器自动输出真实原生图片组件，保持原图的比例和居中方式。已随 `assets/footer.jpg` 留有一份源图字节，方便离线辨认；生成成稿仍使用 `hello-week.template.json` 里原生图片地址。

## 组合方式与可用模板

| 使用场景 | 内容 JSON 范本 | 自动出现的可变栏目 |
| --- | --- | --- |
| 常规周报 | `examples/01-regular.json` | 回顾、预告、投稿、联系、结尾 |
| 多类别/多条资讯 | `examples/02-multicategory.json` | 两期多个分类和多条新闻 |
| 长标题/复杂事项 | `examples/03-long-content.json` | 长资讯、多个时间和截止字段 |
| 百讲预留与重要提示 | `examples/04-performances-notices.json` | 必备空白百讲方框与重要提醒 |
| 精简周报 | `examples/05-brief.json` | 仅后续活动；不出现空回顾和过渡 |

组件顺序由 `scripts/build.py` 自动维护。通常**不要在内容 JSON 里增加 `banner` / `divider` / `code_outro` 之类虚构字段**；需要定制原生结构时，修改组件种子或构建脚本并保留完整原生模型。

## 排版风险审核（出包前）

另请核对百讲演出原生方框**恰好出现一次**，且内部空文本框无历史文案、海报、链接或提示词，位置在后续资讯之后、重要提示之前。

检查每一处被新文案影响的原生容器：**宽高是否固定、`flex` 是否禁止收缩、可见内容是否溢出、图片是否拉伸、装饰层是否遮挡**。具体修复应定位真实子组件，只调整必要的原生样式，保持视觉体系不变。完成静态校验不代表在秀米中实际渲染过。
