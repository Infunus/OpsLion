# 原生组件素材库的语义选用与内容忠实度

> 核心规则：**抓取包描述“有哪些可用组件与视觉语言”；当前文案决定“文章要表达什么、以什么顺序表达”。** 不要把抓取时的页面顺序当作新稿排版顺序，也不要让槽位数量决定原稿篇幅。

## 1. 制作前先完成两份内部清单

### 当前文案大纲（先写，暂时不要分配组件）

从主稿与图片按原顺序整理：

- 标题、导语、章节、小标题、自然段、收束语；记录每段的用途、承接关系和需要强调的关键词。
- 每一段的事实、数字、引语、名称、日期、链接、图片及图注；识别“应出现在哪段附近”的关联。
- 哪些图片是正文主体、哪些是插画/表情/Logo、哪些是装饰；不要默认 ZIP 的图片序号就是插入顺序。
- 区分已经成文的正文和仅用于排版的备注（例如“此处放图”）。注意备注可能还指定位置、尺寸和对齐。

**只有完成文案大纲，才开始挑选秀米组件。**

### 原生组件目录（逐个检查）

`catalog.json` 只给出 slot 原值、位置和来源索引，不能自动保证语义正确。需要查看模块旧文字、文本量、字号、颜色、`tplId`、边框、背景、布局结构、图片容器及邻接装饰，给每个来源模块标注**可承担的用途**与限制：

| 可能用途 | 判断线索 | 使用原则 |
|---|---|---|
| 封面/开场 | 大标题、主视觉、首屏装饰 | 适合表达本期主题，不要塞长正文 |
| 一级/二级标题 | 短文字、强对比、明显留白或强调线 | 对应文案真实标题层级，可复用 |
| 章节过渡/分割线 | 纯图形、横线、分隔文字 | 按内容段落关系插入，可增减 |
| 正文/图文说明 | 多行可伸缩文本、通栏或中宽容器 | 对长段落优先选择，不能被旧篇幅约束 |
| 引言/醒目句 | 少量居中或突出文字、较大留白 | 表达提炼重点，不改写原稿事实 |
| 图片/图注 | 适配图片比例、配套图注 | 按主稿语义与图片内容安排 |
| 时间地点/附注 | 较小文字、标记列表、信息框 | 适合结构化说明，勿拆坏关键信息 |
| 原生数据表格 | `paper-cp:layout/classic-table-normal`，内有 `classicTable1.items[].tds[]` | 阵容/时间线/名单等使用真实可编辑单元格；动态扩行用 `nativeTables` |
| 署名/尾部/固定装饰 | 落款、Logo、二维码、页尾形态 | 看本期要求是否保留、替换或省略 |
| 复合容器 | 多层 `colN/items`、边框和装饰整合 | 优先当整体使用，不擅自抽出中间子件做独立顶层 |

一个模块可能同时承载标题、分割线和正文。判断时记录内部子组件用途，**不能只根据它原来的第一句话或出现在第几位作出分类**。

## 2. 由文案选择组件并重新编排

1. 从当前文案大纲的第一段开始，为各段选合适的组件类型；之后再选择具体的 `source` 以及要编辑的 `slot`。
2. **允许重排、跳过、复用**现有原生模块，`sequence` 与原稿顺序不必相同；章节数、正文块和图片数量按本期内容需要决定。
3. 若某组件不适配文字量，换成相近视觉语言的正文组件，或复制整个合适的文本块；不要一边压缩原稿一边把长文硬塞进短标题。
4. 当原稿需要新增某种用途，但素材库没有独立合适组件，可复用结构最接近的已有原生组件，谨慎在实例上修改已知原生样式；不要凭空虚构原生组件类型，也不要承诺能任意拆分复合子组件。
5. 配图原则上保留原稿出现位置及图注对应关系；确有阅读或排版需要时，可在相关段落附近微调位置并记入变更说明，不能移到不相关章节。
6. 完成模块序列后，检查上下相邻组件的留白、分割线、衔接、对齐和重复装饰。单个模块局部好看还不够。

## 3. 文案改动的边界

**默认原文一字不改**。文案内容与写作风格优先于视觉形式。对于居中孤字行、窄卡片不协调等具体版式问题，允许语义换行和小幅删字、换词、标点调整；无需等到所有布局手段都失败。对于明显原文错误也可合理修正；不因一般审美偏好而全篇润色。每处例外变化都要在交付时说明原因。尤其要保留人物描写、比赛场景、情感重点和全部关键信息，不可把大量段落统一改为语义相近的概括句。

- 先观察实际效果，再选择原生组件/宽度/字号、手动断行或必要的局部改字；**不机械要求先穷尽一切布局方法**。
- 对事实性错误或内部冲突，能核实则修正并记录依据；无法核实则标注问题，不能靠猜测更改姓名、时间、比分或结论。
- 原生表格尽量还原原稿的行列和信息；行列调整时仍完整保留实质数据。
- 图片、图注和原模板品牌尾图/LOGO等有独立的保留清单；只能在保持语义关系时微调图片位置。
- 自动差异工具用于发现原稿→成稿变化，**记录每一项字词/句子增删改**，由编辑逐条审查并在交付时提供清晰的改动说明；参见 `content-fidelity.md`。

## 4. 发布前内容对应检查

建立**逐项内容台账**：`原文段落/表格单元格 → 成稿模块/文本槽位 → 关联图片 → 实际变更及原因`，检查事实、段落重心、人物描写、数字、图文关系；任何删改需能解释且在交付时披露。

`native_packet.py validate` 只管导入结构；另须运行 `verify_source_fidelity.py` 发现并核对文字差异，人工判断调整是否克制、信息是否忠实，并检查图片、无法解析对象与品牌尾图。
