# 中文正文与居中排版规范

规则是编辑判断，不是为所有文本统一套样式。**先分辨段落用途，再选择对齐、换行和缩进**，尽量延续捕获模板的视觉语言。

## 1. 什么适合居中

- 章节标题、简短题签、口号、引语、诗句、独立致谢、落款等，若视觉上需要强调或形成节奏，可以居中。
- 资讯主体、叙事长段、时间地点列表、步骤说明、复杂图注通常更适合左对齐或两端对齐，不宜整篇居中。
- 不能因模板原本是居中框，就把任意新段落硬填进去；应先考虑是否更适合换成正文组件。
- 引文若很长，居中会难以阅读，宜改为左对齐引言块、正文，或保留有意义的段落层次。

## 2. 居中长句如何分行

- 居中段落如显得太长或在手机宽度下参差拥挤，可按逗号、语义短语、并列关系、语气停顿断成 **2–3 行相对均衡的短行**，不必僵化限定行数。
- **首选保留原字原句的语义断行**；如果居中后最后一行只有一两个字，或手动断行仍不均衡，可删去一两个冗余字、微调词语/标点，让文字与版面协调。此类小幅改字允许在有可见排版理由时直接处理，并须在交付时逐项说明；不要借机重写整句话。
- 不在专有名词、人名、数字、时间、成对标点或词组内部任意断开。
- `edits` 给文本 slot 的值中使用 `\n` 表示换行；插件会将其处理成 `<br>`，但不要把一个自然段任意切成大量短句。只有断行而原字句不变时是排版操作；若真删字、换词或改标点，须纳入文案改动记录。
- 在 320px / 375px 等手机正文宽度下检查手动换行与自动折行是否叠加，防止形成新的孤字行。
- **示例**：居中的「欢迎大家共同见证这场精彩纷呈的比赛」末尾只剩「赛」，可以改为「欢迎大家共同见证\n这场精彩纷呈的比赛」；若仍不协调，可适当删去「共同」等非关键信息。前者只记录视觉断行，后者记录实际删字。

## 3. 正文自然段与秀米原生首行缩进

- **是否首行缩进没有固定字数标准。** 先看文本承担的功能：多段连续叙事、议论且版面留白合适时可以考虑 2em；信息卡、列表、时间地点字段、引导语、图注、居中题签、窄栏正文，即使很长也通常无需缩进。不要把“超过若干字”写成触发条件。
- **以用户实际抓取的秀米 v5 数据为准**：秀米“首行缩进 2 字”记录在富文本段落 HTML 上，形式为 `<p style="text-indent: 2em;">正文</p>`，**不应写成** `txt1.style.textIndent`。原版 2.2.0 将缩进当作文字 cell 的 style 属性，已纠正。
- 排版前同时检查**所在位置、容器宽度、段落数量、左右对齐方式、已有段距/底色/边框、是否有列表符号**，判断缩进能否改善层次。如果视觉层级已经清楚，无缩进往往更自然；尤其不能在短窄文本框内叠加缩进造成首行拥挤。
- 新版生成器支持按**模块实例**和**文字 cell**设置 `textFormatting`，只在确认必要时给选中的 `<p>` 自然段写入 `text-indent: 2em;`，不改动字号、字色、段内 `<span>/<strong>` 等格式。若只需要给部分段落缩进，应拆分使用不同原生文本组件或选用不同 cell，不要给整块卡片的标题/列表加缩进。
- 在含多个 `<p>` 的同一 cell 中，缩进对每个自然段生效；`<br>` 是手动换行，不会额外产生一个新的首行缩进。使用前还要检查原模板是否已有缩进，避免重复套用；不要用全角空格冒充秀米原生设置。**不能仅凭文本长度，推断是否要写入 `firstLineIndent`。**

### 判断示例（不设字数阈值）

- **长但不缩进**：浅色信息卡内带小标题、图标和时间地点列表的介绍，或本身已有足够段距的说明，即使数百字也应先保持齐头式段落。
- **可能缩进**：较宽正文区内多段连贯的叙事文字，前后没有额外列表符号或明显分隔，且整体排版采用传统段首标识时，可以对这些自然段统一使用 `2em`。
- **需要逐处判断**：同一篇稿件的导语、正文、引用块和图注可能采用不同段落样式；只在真正适合的实例设置，不将正文规则扩散到全篇。

## 4. 西文打断（长英文/URL）

- 对有**连续很长的英文单词、标识符、网址或文件路径**，且组件文字区较窄、实际可能被英文撑开的情况，考虑启用秀米“西文打断”。对于普通可自然换行的英文段落，不必无条件打开，避免从单词中间截断而降低阅读体验。
- 根据实际抓取包，启用时原生模型同时表现为 `txtN.constraint.wordBreakMode = "breakAll"`，以及段落 HTML 的 `<p style="word-break: break-all;">…</p>`。两者应同步设置。
- 生成器的 `textFormatting.westernBreak: true` 会**仅针对选中模块实例**完成以上两处修改。既有原生设置若已开启，直接保留；不要求手工编辑 HTML，也不建议为全文统一强制开启。
- 审核对连续 40 字符以上的西文串增加 `long-western-run` 提示，**只提示检查**，不等于实际发生溢出。

## 5. 可直接用于构建的文本排版选项

下面的 `path` **相对于一个顶层 `source` 组件**，必须指向实际存在的 `type: "text"` cell。由 AI 根据 `catalog.json` 和原生模型定位，不能把 `txt1` 视为所有稿件的通用路径：

```json
{
  "id": "body-example",
  "source": 0,
  "edits": { "t:[0,\"txt1\"]:0": "一段需要首行缩进的正文" },
  "textFormatting": [
    {
      "path": ["txt1"],
      "firstLineIndent": "2em"
    }
  ]
}
```

这只是字段示意，并非要求中文正文默认缩进。**大多数稿件可以完全不设置 `textFormatting`**；仅在该实例适合缩进时才使用 `firstLineIndent: "2em"`，且只有长英文/连续字符确实影响折行时才考虑 `westernBreak: true`。标题、清单和居中信息卡一般两项都不设。生成器会克隆原生模块并按实例加样式，`edits` 继续只含纯文字；支持 v4 原生协议的导入端 会在替换文字节点时保留原段落的 `<p style=…>`。

若原生 cell 没有 `<p>` 自然段，工具会提示不能安全应用该选项；应选择合适的正文型原生组件，不靠构造未经验证的新类型组件。

## 6. 加粗与强调（必须与原文一致）

- 原稿加粗的正文片段、标题或表格单元格必须继续加粗。普通 `edits` 只替换原生纯文字节点，不能保留源 Word 的任意加粗 runs；局部加粗通过 `richText` 构造独立原生组件变体。具体语法见 `emphasis.md`。
- 本期值得强调的关键信息（如比分、人物高光、时间节点）可以额外局部加粗，但不要默认整段加粗。新增加粗不需要改动原文字句。
- 同级标题的字重统一，优先加粗；同一组件类型若扮演不同语义角色（章节标题与图注）可以采用不同粗细。分组核对见 `emphasis.md`。
- 在本地手机尺寸和真实秀米编辑器中检查加粗导致的换行变化、拥挤和字数误判；加粗造成孤字行时遵循既有的换行/小幅微调原则。

## 7. 与原生设计协调

- 先按语义选合适组件；再调整局部对齐、缩进、行高或必要间距。不要一上来统一改所有标题居中或全文段首加空格。
- 对称装饰适合居中时可保留；正文的首行缩进要与可读行宽配合，容器太窄时可以保持无缩进。
- 修改只作用于本轮使用的组件实例，不影响来源模板和其他引用同一模块的实例。
- 对较窄手机宽度复核孤行、挤压、换行和文字完整性。没有实站渲染时按静态证据说明限制。
